# 技术实现细节

本文记录脚本的内部机制、踩坑记录与排障手段。**只想用的话看 [README](../README.md) 就够了**，
这里的内容面向改代码、排故障、或者想搞清「为什么这么写」的场景。

---

## 一、工作原理（重要）

```
┌─ 顶层窗口 (115.com/?cid=...) ──────────────────────┐
│  「标签」控制面板挂这里                              │
│  负责：UI、数据源请求、写本地库、资料库搜索/筛选/播放   │
└──────────────────┬────────────────────────────────┘
                   │ postMessage 双向通信
                   ▼
┌─ 文件列表 iframe (?ct=file&ac=userfile&tpl=view_large) ─┐
│  115 真正渲染文件列表的地方（1332x758）                  │
│  负责：扫描文件名、提取番号、把结果回报给顶层             │
└──────────────────────────────────────────────────────┘
```

**关键事实**：115 网页版把文件列表渲染在**同源 iframe** 里，顶层 DOM 几乎是空壳。
所以脚本不带 `@noframes`，会同时在顶层和所有 iframe 注入，各自判断角色后分工：

| 角色 | 判定依据 | 职责 |
|---|---|---|
| 文件列表 frame | URL 含 `ct=file&ac=userfile`，或内容含视频文件 | 扫描文件名、提取番号、回报结果 |
| 顶层窗口 | `window.top === window.self` | 挂面板、查数据源、写资料库、搜索筛选、播放 |

**教训：检测点必须放在「元素真正出现的那一侧」。** 在 A 页面检测只在 B 页面挂载的
DOM，永远是 false，而且不报错、极难发现。脚本里栽过两次（见下文「播放方式」）。

## 二、收录流程：接口主力 + 增量比对 + DOM 兜底

```
顶层面板点「收录本目录」
  │
  ├─① 顶层读 URL 拿 cid → 调 webapi.115.com/files（show_dir=1，自动翻页 1000 条/次）
  │     → 拿到全目录条目（自带 pickcode / fid），顺序与网页一致 → 记下每条 dirIndex
  │     接口不可用时 ↓
  ├─② broadcast('harvest') → 列表 frame DOM 扫描当前页
  │     → broadcast('harvest-items') 回报（注意：只能收当前页）
  │
  ├─③ 读 library 表里本目录已有记录（走 cid 索引）→ 分成 新增 / 待补 / 未变 / 失效
  │     → **只对 新增 + 待补 的番号查数据源**（未变的一条都不请求）
  ├─④ 写库 + 标记失效 + 更新 dirs 汇总 → 刷新资料库页签
  └─⑤ 面板显示「新增 N · 补查 M · 未变 K · 失效 W」
```

网页版列表每页只渲染 24 条，**78 页的目录靠 DOM 扫描永远只能收到第一页**。
所以收录优先走 115 自己的 webapi —— 它支持一次拿上千条（脚本自动翻页，
1000 条/次，1872 条的目录两次请求搞定），并且**直接返回 `pickcode`**
（播放接口唯一必需的参数）。

为什么要保 ②：接口在未登录 / 改版 / 被限流时会失败，那时至少还能收到当前页。
但两条路的**覆盖面差别巨大**，所以提示语里会明确说「这种方式只能收当前页」。

收录是**逐目录手动触发**的，没有全盘递归 —— 手动巡航最稳，也不容易触发风控。

### 接口分页有个坑

`webapi` 在有些情况下**不返回 `count` 字段**。早期实现写成
`total = Number(json.count) || list.length`，于是第一页的 1000 条被当成总数，
立刻判定「已拿齐」→ 78 页的目录只收到第一页，**而且完全不报错**。

现在只有 `count` 是 `> 0` 的有限数才采信，否则置 `null`，改为靠「某一页拿空」终止。
这条已在 `tests/test_api.mjs` 里固化。

### `cid` 只能由顶层提供

实测 115 列表 iframe 的 URL 里 `cid=0`：

```
顶层 URL     https://115.com/?cid=3527255730090411997&offset=0&mode=wangpan   ← 对
列表 frame   https://115.com/?ct=file&ac=userfile&tpl=view_large&...&cid=0    ← 错
```

早期版本在列表 frame 里取 `cid`，导致全库 `cid=0`、点播放跳到网盘根目录。
现在 `doHarvest()` 一律用顶层的 `getCurrentCid()`，列表 frame 报上来的只作兜底。
重新收录时会自动清掉同文件的旧记录（`pruneLibraryDuplicates`），
所以**升级后重收一遍即可修好历史数据**，不会产生重复条目。

### `pickcode` 从哪来

两条路，优先级从高到低：

1. **115 接口返回值里的 `pc` 字段**（主力）—— 收录走接口时每条都带，100% 覆盖
2. **从文件行的 DOM 属性里挖**（兜底）—— 实测真实属性名是 **`pick_code`（带下划线）**，
   挂在 `<li rel="item">` 上：

   ```html
   <li rel="item" title="hmpd-10044.mp4" file_id="3527247704331650213"
       pick_code="bi0izro13wfpq8syt" file_size="6984372848" cid="3063507632273050" ico="mp4">
   ```

   ⚠️ 早期只找 `pickcode` / `data-pickcode` / `data-id`，
   **一个都匹配不上**（探针实测覆盖率为 0），白折腾了一轮。
   同理 `file_id`（不是 `data-id`）、`file_size`（不是文本里的「6.50GB」）。
   现在同一批候选里全都试，并在 `tests/test_rowkeys.mjs` 里固化了真实结构。

第 2 条还有个必须加的闸门：`rowEl` 必须确认是**单行的容器**。115 的 `<li>` 父节点 `<ul>`
装着所有行，一旦把它当行容器，`querySelectorAll` 会扫到别的文件的链接，
把 A 的 pickcode 安到 B 头上（表现为「点这个播那个」）。

### 判断「这个容器装了多个文件吗」不能数扩展名出现次数

同一个文件名被拆段渲染时（`<span>PI</span><span>YO-046.mp4</span>` → 文本
`PIYO-046.mp4YO-046.mp4`）扩展名会出现两次，但那明明是**一个**文件。
数次数会把这种行判成「多文件」，导致同一部片被拆成两条记录。

现在改成收集所有文件名令牌，只有「不能全部被最长那个包含」才算真的多文件
（令牌正则须**惰性** `{1,160}?`）。

### `dirIndex`：为什么收录时要记住文件的位置

接口拉清单时带了 `show_dir=1`，所以拿到的顺序和网页看到的一致。脚本会记下每个
文件在**整个目录清单里的位置**（`dirIndex`）。它只有一个用途 —— 点播放时算
「该翻到第几页」。115 网页列表每页只渲染 24 条，78 页的目录里目标文件很可能不在
第一页，没有这个信息就会「跳回目录但什么都没找到」。

## 三、播放：两条路各自的坑

### 页面内打开（模拟点击）

模拟点击要成功，得同时满足这几件事：

| 条件 | 为什么 |
|---|---|
| 点**那个 `menu="view_file_one"` 的 `<a>`** | 115 的动作是「委托 + `menu` 属性」驱动的，点 `<li>` 毫无反应 |
| 行容器必须是**单行**的 `<li>`，不能上溯到 `<ul>` | `<ul>` 里所有文件都在，取属性会串号 |
| 先 hover 再点 | 有些视图要先 hover 才把工具栏（含播放按钮）插进 DOM |
| 事件序列要完整 | 有的实现监听 `mousedown`/`mouseup` 而不是 `click` |
| 成功判据要看**顶层 + 所有同源 iframe** | 播放器不一定开在列表 frame 里 |

实测 115 的列表行长这样：

```html
<li rel="item" title="hmpd-10044.mp4" file_id="3527247704331650213"
    pick_code="bi0izro13wfpq8syt" file_size="6984372848" ico="mp4">
  <a class="name" href="javascript:;" menu="view_file_one" rel="file">
    <span>hmpd</span><span>-10044.mp4</span>
  </a>
  …
</li>
```

打开动作绑在那个 `menu="view_file_one"` 的 `<a>` 上，**点 `<li>` 毫无反应**。
而扫描器早先命中的恰恰是 `<li>`（因为它带 `title`），于是脚本第一层就点错了元素。

所以 `triggerRowOpen()` 会：先精确点 `clickEl`（带 `menu` 的那个链接）→ 失败再逐层
向上试（4 层 → `nameEl` → `rowEl`），每层「先 hover → 找播放按钮 → 完整 click 序列
→ 补一次 dblclick」，任一步出现「真的加载了内容的 `<video>`」就算成功。
检测范围包括**顶层窗口和所有同源 iframe**。

全失败则把该行 HTML 打到控制台，并引导用户用面板上的 **🎬 采样视频行结构** 回报真实结构。

> **成功判据不能只看「存在 `<video>`」** —— 115 页面常驻一个没有 `src` 的空骨架，
> 那样判会恒真。必须要求 `video.src` 有值 / `readyState > 0` / 有 `<source src>`。

### 直接打开播放页

**默认地址是 115Master 的唤起路由**：

```
https://115.com/web/lixian/master/video/?pick_code={pickcode}&cid={cid}
```

`pick_code` 必填、`cid` 选填 —— 这是 **115Master 脚本**注册的虚拟路由，
115 服务器本身不认识它，**没装 115Master 时打开会是空白页**。

#### 为什么默认不再是「自动检测」

早期版本有个 `auto` 模式：检测到 115Master 就开播放页，否则回目录模拟点击。
但 115Master 的 DOM 标记（`#master-app` / `x-player`）**只在播放页挂载**，
在文件列表页上永远检测不到 —— 于是 `auto` 事实上被静默降级成了「回目录模拟点击」。
用户看到的现象就是**点了播放却跳回目录、还提示找不到视频**。

检测点放错了页面，后面再怎么调都是白搭。现在按设置直着走，不在中间偷偷改道。

#### 播放页自检

脚本在播放页里也会被注入，而那一侧才判断得准。做法：

- 播放页里轮询「播放器是不是真的起来了」——判定要求 `<video>` 有真实 `src`
  （原因见上，只判存在会恒真）；
- 结论写进 `localStorage`（10 分钟有效）；
- 列表页下次点播放前先读一眼，上次是白屏就先提醒；这次打开后也会「盯着」结果，
  一旦回报白屏，立刻弹提示并说明两条出路；
- 白屏时页面上还会直接浮出一张说明卡片，写清「这个地址需要 115Master」
  以及「装插件」/「改用页面内打开」两条路。

**时序坑**：`window.open` 打开的是**后台标签**，浏览器会把后台标签的定时器节流到
≥1s/次。所以自检超时给到 20s，并额外监听 `visibilitychange` ——
**用户切过来看见白屏的那一刻，才是该下结论的时刻**。首次使用时缓存是空的，
这条路径是唯一能及时给反馈的通道。

### 缺 `pickcode` 的老记录

播放地址里 `pick_code` 是必填项，旧版本收录的记录可能没有。这种条目在资料库列表里
会带一个 `缺提取码` 角标，统计行也会汇总数量；进该目录点一次「📥 收录本目录」
即可补全（增量收录只补这一条）。

## 四、数据表设计要点

数据存在浏览器 IndexedDB（库名 `jv115-tagger`，5 张表）：
`meta` / `fileMap` / `library` / `dirs` / `settings`。

`library` 表的 `id` 用 `cid@@fileName`：

- 同名文件在不同目录是两个条目，不会互相覆盖
- 目录内改名会产生新条目（旧的留给你手动清理）

每条记录还带 `dirIndex`（在目录清单里的位置）、`pickcode`、`gone`（已失效）、
`firstSeenAt` / `lastSeenAt`（增量收录靠它判断「这次目录里还有没有」）。

`dirs` 表按 `cid` 记录每个收录过的目录：收录时间、视频数、上次新增几条。
面板进到该目录时读它来提示「上次收录于 X 天前」。**只读本地，不发网络请求。**

`actresses` / `genres` 建了 **multiEntry 索引**，所以「按某个演员查全部作品」可以直接走索引。
不过当前筛选是在内存里做的（`filterLibraryRows`，纯函数、好测）—— 库规模到万级再考虑改用索引游标。
渲染侧则分批进行，见下一节。

> `DB_VERSION` 从 2 升到 3 时新增了 `dirs` 表。建表一律用 `contains` 包住，
> **绝不 drop 旧表**，否则用户数据会被清空。

## 五、资料库列表：分批渲染（懒加载）

### 问题不是「渲染不出来」，而是「没说清还有多少」

v1.3.0 之前的实现是：

```js
list.innerHTML = rows.slice(0, 300).map(/* … */).join('');
```

两个毛病叠在一起：

1. **静默截断**：命中 3869 条时只渲染 300 条，界面上**没有任何提示**
   说明「还有 3539 条没显示」。用户只会觉得「筛选完显示不全」。
2. **两层嵌套滚动**：`.lib-list` 写死 `max-height: 320px; overflow-y: auto`，
   而外层 `.body` 也是 `overflow-y: auto` —— 43 条结果挤在 320px 的窗口里滚，
   手感很差，滚到边界后会不会接力滚外层还得看浏览器实现。

用户的原话是「发现不能显示全部结果，也没有翻页功能」。所以真正缺的并不是
「翻页控件」，而是**分批加载 + 明确的总数反馈**。

### 改法

`core/paging.js`（纯计算，可单测）+ `panel.js`（只管 DOM）：

| 成员 | 职责 |
|---|---|
| `LIB_PAGE_SIZE` | 每批 50 条 |
| `libPageWindow(total, shown, size)` | 算出 `[from, to)` 窗口、本批条数、是否还有更多 |
| `libFootText(total, shown, loading)` | 底部状态文案 |

渲染侧：

- `renderLibList()` 只渲染第一批，并在列表末尾放一个 `.lib-foot` 哨兵；
- `IntersectionObserver` 盯着哨兵（`root` 指向列表本身，
  `rootMargin: '0px 0px 160px 0px'` 提前 160px 触发），一进入视口就追加下一批；
- 底部恒显「已显示 X / 共 Y 条 · 继续下滑自动加载」，
  **加载完改写成「已全部显示（共 Y 条）」** —— 这句是关键：
  少了它，用户滚到底没等到新内容，仍会怀疑「是不是还有没加载出来的」；
- 观察器不可用时退化成「加载更多」按钮，不静默失败。

### 布局：让滚动只发生在一处

```css
.body { display: flex; flex-direction: column; }   /* 内容区变 flex 容器 */
#pane-library.active {                             /* 资料库页吃满剩余高度 */
  display: flex; flex-direction: column;
  flex: 1 1 auto; min-height: 0;                   /* 关键：允许收缩 */
}
.lib-list { flex: 1 1 auto; min-height: 180px; }    /* 原来是 max-height: 320px */
```

`min-height: 0` 是 flex 滚动区的必要条件 —— flex item 默认 `min-height: auto`，
不会收缩到比内容更小，于是列表永远撑破容器、无法内部滚动。

### 边界要钉死在测试里

- **窗口遍历不重不漏**：一直滚到底，所有下标必须恰好覆盖一次；
- **非法 `size` 不能退化成 1**：`Math.max(1, size || DEFAULT)` 是错的 ——
  负数是 truthy，会被 `max` 抬成 1，变成「一次只加载一条」。
  `tests/test_paging.mjs` 里专门有一例钉这个；
- **输入不能产生 NaN**：`slice(NaN, NaN)` 不报错、直接返回空数组，
  表现是「列表一片空白但控制台干净」—— 最难查的一类 bug。

## 六、标题中译：纯本地怎么做到可用

### 为什么不上翻译接口

调翻译 API 看着更省事，但有三条硬伤：

1. **内容类型会被拒答。** 成人向片名触发审核策略时，接口返回的不是译文，
   而是拒绝、或者被「净化」过的文本。
2. **几千条是一笔持续开销**，而换来的只是「更通顺」。
3. **接口挂了就没有译文**，本地方案不会有这个问题。

所以目标定成**看得懂**，不是信达雅。代价是长句不成句 —— 这个取舍是明确的，
写下来免得以后有人以为是没做好。

> **如果以后要评估联网方案**，本机实测的连通性（2026-09）：
> `translate.googleapis.com` 不通（国内常态被墙）；
> `api.deepseek.com`、`api.moonshot.cn`、`fanyi-api.baidu.com`、`api-free.deepl.com`
> 都能连上，但**都需要 key**。其中 DeepL 是境外服务，
> 对付日文成人向标题被拒答的概率明显低于国内厂商 —— 真要接，先拿 20 条真实标题试拒答率，
> 再决定，别先写代码。

### 流水线

```
原文
 ① 专名占位       番号 / 演员名 → \u0001N\u0002
 ② 术语表替换     最长优先的正则 alternation
 ③ 助词处理       の→的；其余助词要求左边紧邻中日文，避免咬到词首
 ④ 字形归一化     日文旧字形 → 简体（必须早于回填）
 ⑤ 清洗           标点 / 空格 / 重复词
 ⑥ 统计残留假名   ★ 在回填之前统计
 ⑦ 专名回填
```

### 四个容易踩错的点

**1. 专名必须先占位。**

演员名是日文，逐字替换会变成一串毫无意义的汉字；番号会被拆开。
演员名的匹配还要容忍网页改写空格 —— 把名字的每个字符用 `\s*` 串起来：
`倉\s*本\s*す\s*み\s*れ`，这样 `倉本 すみれ` 也能命中。

**2. 统计假名必须在回填之前。**

被保护的专名本身就是日文。回填后再统计，会把它们算成「没译到」，
于是**每条带演员名的标题 coverage 都虚低**，这个指标就废了。
（这条是写测试时才发现的，代码里已注明。）

**3. 必须做字形归一化。**

术语表只能收整词，剩下的汉字会原样流下来 —— 而它们是日文写法：

| 原文 | 不归一化 | 归一化后 |
|---|---|---|
| `夫婦交換` | 夫婦交換 | 夫妻交换 |
| `家庭教師の誘惑` | 家庭教師の誘惑 | 家教的诱惑 |
| `専属決定` | 専属決定 | 专属决定 |

字形表的关键约束：**只收「日文这么写、中文不这么写」的字**。
中日同形字混进去就会把本来正确的字改错。两批都要收：

- **日文新字体**（`図`/`厳`/`拡`/`譲`/`価`/`駅`/`産`）——
  日文战后自己简化过一轮，方案和中文并不一致（日文 `図` = 中文 `图`）
- **舊字體**（`屬`/`換`/`誘`/`婦`）—— 日文与繁体同形，中文已简化

代码里对字形表做了容错：解析时跳过格式不对的条目、跳过左右相同的条目，
同一字映射到两个结果时保留先出现的并告警。这样表里手滑写错一条也不会改错字。

**4. 助词规则会误伤。**

`が` 在 `昼下がり` 里不是助词，删掉就变成「昼下り」。
所以助词替换要求「左边紧邻中日文字符」（词首的助词不动），
并且**术语表在长度上优先** —— 补救办法是把整词收进词典（`昼下がり → 午后`）。
漏掉的词会在「译名对照」里以「未译」列出来，照着补即可。

### 缓存失效：把词典版本混进哈希

```js
hashTitle(t) = djb2(normalize(t) + '#v' + GLOSSARY_VERSION)
```

这一条是「词典可维护」的前提。漏了它，用户加了词却发现老标题纹丝不动，
只会以为功能坏了。混进去之后：改词典 → 哈希全变 → 自动重译。

**没命中的条目也要记哈希**，否则每次都会把同一批未命中条目重新算一遍。

### 落库与同步

- 译文存在 `meta` 里（按番号，一部片只译一次）
- `library` 是列表渲染的数据源，存的是**副本** →
  `applyTitleZhBatch()` 必须同时更新两处。只写 `meta` 的话列表里看不到译文，
  得重收一次目录才生效 —— 那个体验很差
- 加字段**不需要升 DB_VERSION**（只有新增 store / index 才需要）；
  旧记录读出 `undefined`，代码用 `?? ''` 兜住

### 维护方式

```bash
node tools/glossary-gaps.mjs 备份.json       # 按出现次数看缺哪些词（补词典用）
node tools/preview-translate.mjs "日文标题"   # 看单条效果，不用开浏览器
```

面板「🈶 译名对照」按覆盖率**升序**列出最差的 25 条 + 缺的词。
把「补词条」变成一个有明确输入的循环，而不是靠感觉 ——
这也是为什么这两个工具值得单独做出来。

## 六之二、v1.4.1：三个「看起来都一样」的教训

v1.4.0 上线当天就被反馈「**大部分没翻译 / 没生效**」。查下来
翻译逻辑没问题，问题在**展示**和**统计口径**上，三个都值得记下来。

### 1. 统计口径错了，比功能坏了更难发现

v1.4.0 的「已译 N 条」判据是 `!!titleZh`，而 `titleZh` 只要
**有一处改动**就会被写进去。于是：

- 一条只把 `同窓会` 替成 `同窗会`、其余全是日文的标题 → 计入「已译」
- 一条完整译名 → 同样计入「已译」

面板显示「已译 3293 条」，用户翻列表却觉得「大部分没生效」。
**两边都没说谎，是指标本身没有区分能力。**

改法：把**覆盖率**一起存进记录（`titleCoverage`），按 `FULL_COVERAGE = 0.75`
分三档报（译得动 / 半译 / 完全没译），角标也跟着分成 `译` / `半`。

> 教训：一个只会「真 / 假」的指标，在「部分成功」是常态的功能里等于没有指标。

### 2. 覆盖率必须存下来，不能在渲染时重算

覆盖率是在 `translateTitle()` 里算出来的。如果渲染时想重新统计，
就得把原文再翻一遍 —— 列表几千条，滚动渲染时这么干会卡。
所以翻译当次就写进记录，渲染只读。

⚠️ 连带一个坑：`applyTitleZhBatch()` 里那句「译文没变就不写回」的省 I/O 判断，
**必须把 `titleCoverage` 也比进去**。只比 `titleZh` 的话，
老记录补覆盖率这一步会被整个跳过，列表永远拿不到「译得动 / 半译」的区分。

### 3. 默认常驻两行，是「信息都在但不好用」

v1.4.0 默认「中文主行 + 原文副行」。信息是全的，但每条都撑成两行，
列表扫起来反而费劲。改成一行的中文，**原文放进 `title` 属性（悬停才看）**：

- `titleDisplayParts()` 多返回一个 `hover` 字段，规则统一：
  `hover = 原文 !== 主行 ? 原文 : ''`
- `sub` 只在用户主动切到 `zh-ja` 模式时才非空，所以渲染那段不用改逻辑

> 教训：**默认值要选「扫得快」，不是「信息全」**。原文不是不显示，
> 是不该常驻占位。

### 4. 顺带记一个测试基建的坑

`storage.js` 新增了 `import { FULL_COVERAGE } from './glossary.js'`，
结果 `test_library.mjs` / `test_play.mjs` 双双崩溃 ——
它们的加载器只剥 `export`，没剥 `import`，于是
`new Function` 里出现 `import` 语句 → `SyntaxError: Cannot use import statement outside a module`。

改法：这些测试的 strip 函数要**同时剥 import 和 export**，
并且把 `glossary.js` 一起注入（`build.mjs` 的 `MODULE_ORDER` 也把
glossary 挪到了 storage 前面，同一作用域里 `const` 有暂时性死区）。

> 这次崩溃**没有产生断言失败**，只是文件级崩溃 —— 再次说明判据必须是
> **进程退出码**，靠「输出里有没有 ❌」会漏掉。

### 5. 天花板要写进文档，不要留给人自己发现

`glossary-gaps.mjs` 会把未译内容分成两类报，这个区分比排序本身更重要：

| 类别 | 例子 | 能否补 |
|---|---|---|
| 可补的**词** | `同窓会` `イキづらい` `あなた` | 加进词典就有用 |
| **语法碎片** | `い` `が` `く` `った` `かれた` | **补不了** |

第二类不是词，是动词活用和助词被切剩下的尾巴。术语表是「词对词替换」，
对它无能为力（词典也明文禁收单字词条，否则会把别的词撕开）。

实测一批真实标题：平均覆盖率 **56%**，译得动 **0 条**，未译的几乎全是碎片。
所以「再补点词就好了」是错的 —— **天花板在这个方法本身**，
不在词典大小。文档必须把这个讲清楚，否则用户会一直在补词里打转。

## 七、历史设计：小圆点（已弃用）

> 以下内容记录 v1.1.x 的旧方案，**v1.2.0 已不再使用**。
> 保留是为了排障时对照，以及说明为什么某些代码看起来「没人调用」。

旧版在文件名旁插一个 6px 小圆点，悬停弹出信息浮层：

```
SONE-119.mp4  ●          ← 平时就是这样
              ▲
              └─ 鼠标移上去 → 弹出标题/演员/类别
```

弃用原因：需求改为「用搜索筛选代替逐条悬停」，信息集中到资料库面板更高效。

### 样式注入的两个作用域（踩坑记录）

脚本有两套样式，注入位置**不同**，改代码时别混：

| 样式 | 注入位置 | 作用对象 |
|---|---|---|
| `STYLES` | Shadow DOM（`ensureHost` 里） | 控制面板（悬浮球、抽屉、资料库、Toast） |
| `TAG_STYLES` | **宿主 document**（`ensureTagStyles`） | 旧版的圆点与悬停浮层（现已不用） |

**为什么必须分开**：旧版的圆点（`.jv-dot`）和浮层（`.jv-tip`）是插进
**115 页面自己的 DOM** 的，而宿主页面的元素**完全不受 Shadow DOM 内部样式表影响**。
早期版本把 `.jv-*` 样式留在 `STYLES` 里，结果圆点是个宽高为 0 的空 `<span>`，
肉眼根本看不见。资料库面板全部在 Shadow DOM 内，不受此影响。

### 一个文件出现两个圆点（旧 bug）

同一个文件的文件名可能同时挂在「外层容器」和「内层文本节点」上，两个都会命中扫描。
旧版做了双向去重：扫描器按「更深/更短者优先」只保留最具体的节点；渲染层再做一次
**限定在本行范围内**的清理兜底。清理**必须严格限定在本行** —— 早期实现向上找第一个
含圆点的祖先，会越过本行命中整个列表容器，把此前所有行渲染好的圆点全清掉。
现在改成：向上逐层清，**一旦遇到挂着其它文件名的容器就立刻停止**。

## 八、调试

### 面板自带的诊断按钮（推荐）

打开面板 → 扫描页，右下角这一排都是排障用的：

| 按钮 | 作用 |
|---|---|
| 🔍 诊断问题 | 把关键指标渲染到列表区，详细报告输出到控制台 |
| 📋 复制诊断摘要 | **一键复制纯文本摘要到剪贴板**，直接粘贴就能发给开发者 |
| 🧬 DOM 采样 | 打印含视频扩展名元素的 `outerHTML` 片段 + 元素路径 |
| 🔬 建库/播放入口探针 | 报告 `fileId` / `pickcode` / 播放链接的覆盖率（跑在列表 frame） |
| 🎬 采样视频行结构 | **自动播放没生效时用这个** —— 把视频行的 HTML、行内所有可点元素、层级链整理成文本并复制到剪贴板 |

诊断摘要包含「**页面框架体检**」：会报告 body 文本长度、关键容器命中数、疑似列表容器清单、iframe 情况。
**如果列表容器为 0 个，说明文件列表根本没渲染** —— 这时改选择器是没用的。

### 控制台命令

如果 115 页面上没反应，按 F12 打开控制台执行：

```js
__jv115.diagnose()           // 完整诊断报告（对象）
__jv115.diagnoseText()       // 纯文本摘要（可直接复制）
__jv115.probeLibrary()       // 建库/播放入口探针（fileId / pickcode / 播放链接）
__jv115.apiFetchDirAll(cid)  // 直接调 115 接口拉全量目录（验证接口是否可用）
__jv115.pickVideoRows(rows)  // 从接口结果里过滤视频
__jv115.sampleRowStructure() // 采样第一个视频行的结构（排查播放触发）
__jv115.triggerRowOpen('x.mp4') // 手动触发某个文件的「打开/播放」，返回试过的方式
__jv115.detect115Master()    // 页面上是否装了 115Master
__jv115.surveyGlobalOpeners()// 列出 window 上像「打开/播放」的全局函数
__jv115.inspectPage()        // 只做页面框架体检
__jv115.inspectAllFrames()   // 逐个体检所有 frame（定位列表在哪个 frame）

__jv115.waitForVideoItems()  // 等待列表渲染（返回 Promise）
__jv115.dumpItems()          // 扫描到的视频条目
__jv115.dumpFileLikeNodes()  // 页面上所有「像视频文件」的节点 + 祖先链
__jv115.dumpRawDom(3)        // 原始 DOM 采样（outerHTML 片段）
```

> 注意：`__jv115` 只在**当前 frame** 可用。想看列表 iframe 内部情况，
> 在 DevTools 的 Console 左上角「top」下拉框里选中 `?ct=file&ac=userfile...` 那个 frame 再执行。
>
> **探针必须跑在列表 frame**：顶层 DOM 抓不到真实的文件行（`fileId` 全空、
> 播放链接全是导航菜单）。面板上的「🔬 建库/播放入口探针」按钮会自动转发到
> 列表 frame 执行，再把结果回传顶层写入剪贴板 —— 直接用这个按钮最省事。

### 常见失败提示含义

| 提示 | 含义 | 处理 |
|---|---|---|
| 没找到视频文件…（含「页面里没有任何列表容器」） | **文件列表没渲染出来** | 确认页面能看到文件；重新登录；清缓存；换 Chrome/Edge |
| 没找到视频文件…（含「发现 N 个疑似列表容器」） | 列表渲染了但内容不含视频扩展名 | 点📋复制诊断摘要发我 |
| 当前目录没扫到视频文件 | 收录时列表帧没扫到东西 | 确认已进入有视频的目录；等列表加载完再点一次 |
| 找到 N 个视频，但文件名里没有可识别的番号 | 文件名不含番号（如「第01集.mp4」） | 正常现象，记录会入库但标为「未获取到标签」 |
| X 抓取被拦截 | Cloudflare 验证 | 先在浏览器新标签页打开该站点过一次验证 |

### 诊断摘要里的关键字段

| 字段 | 怎么读 |
|---|---|
| `元素总数 === 叶子节点数` | 页面没有嵌套容器 → 是纯 UI 页，列表不在这个 frame |
| `页面扩展名分布: {}` | 这个 frame 的文本里没有任何视频文件名 |
| `跨frame扫描 → 各frame` | 每个 frame 扫到几个视频，一眼看出列表在哪个 frame |
| `各frame体检 → 可能的列表容器` | 哪个 frame 里有列表结构，容器有多少项 |
| 探针里的 `顶层帧 / 列表帧` | **必须是 `顶层帧: false \| 列表帧: true`**。若反了说明探针跑错 frame，结论全部无效 |
| 探针里的 `有 pickcode 的条目: N/M` | M 条里有多少能拿到播放所需的 pickcode。为 0 时播放会走「跳回目录」 |

DMM 官方 API 返回的数据最结构化（含封面、简介），但需要免费申请
